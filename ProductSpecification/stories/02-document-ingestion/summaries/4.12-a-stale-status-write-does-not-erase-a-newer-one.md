## design (2026-11-09)

**Decision:** First terminal status wins — `Document.prefer_terminal` keeps a finished row when a later save brings a different status; Memory / Fake / Postgres `save` apply that choice (Postgres under `SELECT … FOR UPDATE`).
**Why:** Two loads taken while indexing can both transition locally; last-write-wins would erase an earlier ready with a stale failed (or the reverse).
**Where applied:** `backend/domain/document/document.py`; intake `save` in Fake, Memory, Postgres; acceptance holds two loads and posts `/acceptance/documents/{id}/stale-save` so the second write is not a fresh re-read `/move` (illegal after 4.8).

## green-usecase (2026-11-09)

**Quirk:** Sanity fail needed a blind Fake `save` — with `prefer_terminal` already in Memory/Postgres the red was only visible on Fake.
**Where:** `backend/usecase/tests/document/test_stale_status_write_does_not_erase_newer_one.py`
**Implication:** Keep Fake on the same prefer-terminal path as production intakes.

## green-acceptance (2026-11-09)

**Surprise:** Sequential `/move` ready→failed is 409 after 4.8; the scenario needs two frozen indexing snapshots, not two re-reads.
**Impact:** Probe `hold_two_loads` + `stale-save` endpoint; pieces still seeded before the terminal writes.
